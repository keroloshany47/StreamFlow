# Java Transaction Producer

High-throughput Kafka producer written in Java. Generates synthetic financial transactions and publishes them to the `financial_transactions` topic at maximum speed using a multi-threaded executor pool sized to available CPU cores.

> This producer is optimized purely for throughput — it fills the Kafka topic with normal-range transactions so the Spark aggregation query has meaningful volume to work with. For anomaly testing, run the Python producer alongside it.

## How It Works

```
main()
  │
  ├── createTopicIfNotExists()     AdminClient checks / creates topic
  │
  ├── KafkaProducer<String,String>  shared across all threads (thread-safe)
  │
  ├── Thread 0  → throughput reporter (logs records/sec every 1s)
  ├── Thread 1  → infinite produce loop
  ├── Thread 2  → infinite produce loop
  └── Thread N  → infinite produce loop   (N = CPU cores − 1)
```

Each producer thread runs an infinite loop:
1. `Transaction.randomTransaction()` — generates a randomized transaction
2. `ObjectMapper.writeValueAsString()` — serializes to JSON (thread-local mapper, no contention)
3. `producer.send()` — fully async send with a callback that increments the global counter on success

A dedicated reporter thread logs throughput every second using an `AtomicLong` counter, so you get a live view of records/sec without any locking overhead in the hot path.

A shutdown hook flushes all buffered messages before the JVM exits on `Ctrl+C`.

## Transaction Schema

Generated by `Transaction.randomTransaction()`:

| Field | Type | Example | Range |
|---|---|---|---|
| `transactionId` | String (UUID v4) | `a1b2c3d4-...` | random UUID |
| `userId` | String | `user42` | user0 – user99 |
| `merchantId` | String | `merchant7` | merchant0 – merchant49 |
| `amount` | double | `234.57` | $10.00 – $510.00 |
| `transactionTime` | long (epoch ms) | `1715500000000` | current system time |
| `transactionType` | String | `purchase` | purchase / refund |
| `location` | String | `NY, USA` | NY, USA / LA, USA |
| `paymentMethod` | String | `credit_card` | credit_card / debit_card |
| `isInternational` | boolean | `true` | true / false |
| `currency` | String | `USD` | USD / EUR |

> The amount range ($10–$510) is intentionally kept below the Spark anomaly threshold of $140,000. To inject anomalies from the Java producer, change the amount range in `Transaction.randomTransaction()`.

**Key schema difference from Python producer:** `isInternational` is a native Java `boolean` here, serialized by Jackson as a proper JSON `true`/`false`. The Python producer serializes it as a string `"True"`/`"False"`. The Spark job normalizes both during ingestion.

## Kafka Configuration

```java
props.put(ProducerConfig.BATCH_SIZE_CONFIG,              524288);    // 512 KB
props.put(ProducerConfig.LINGER_MS_CONFIG,               10);
props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG,        "snappy");
props.put(ProducerConfig.ACKS_CONFIG,                    "1");
props.put(ProducerConfig.BUFFER_MEMORY_CONFIG,           268435456L); // 256 MB
props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);
props.put(ProducerConfig.SEND_BUFFER_CONFIG,             1048576);   // 1 MB
props.put(ProducerConfig.RECEIVE_BUFFER_CONFIG,          1048576);   // 1 MB
```

| Config | Value | Why |
|---|---|---|
| `BATCH_SIZE` | 512 KB | Large batches = fewer network round trips |
| `LINGER_MS` | 10ms | Wait to fill the batch before sending |
| `COMPRESSION_TYPE` | snappy | Fast compression, ~2–3x size reduction, low CPU cost |
| `ACKS` | 1 | Leader ack only — maximum throughput, small durability tradeoff |
| `BUFFER_MEMORY` | 256 MB | In-memory buffer before backpressure kicks in |
| `MAX_IN_FLIGHT` | 5 | Up to 5 unconfirmed requests per connection |
| `SEND_BUFFER` | 1 MB | OS-level TCP send buffer |

**Topic configuration:**

| Config | Value |
|---|---|
| Topic name | `financial_transactions` |
| Partitions | 16 |
| Replication factor | 3 |
| Bootstrap servers | `localhost:29092,39092,49092` |

## How to Run

### Prerequisites

- JDK 11+
- Gradle (wrapper included — no installation needed)
- Kafka brokers running via `docker compose up -d`

### Build

```bash
./gradlew build
```

### Run

```bash
./gradlew run
```

Or via the pre-built JAR:

```bash
java -jar build/libs/KafkaSparkArch-1.0-SNAPSHOT.jar
```

### Expected output

```
INFO  Starting 8 producer threads on 8 cores
INFO  Topic 'financial_transactions' already exists.
INFO  Throughput: 280,000 records/sec | Total: 280,000
INFO  Throughput: 310,000 records/sec | Total: 590,000
INFO  Throughput: 295,000 records/sec | Total: 885,000
```

### Graceful shutdown

`Ctrl+C` triggers the JVM shutdown hook — it flushes all buffered messages before exit:

```
INFO  Shutting down — flushing remaining messages...
INFO  Done. Total sent: 4,200,000
```

## Scaling

The producer automatically uses all available CPU cores:

```java
private static final int NUM_THREADS = Runtime.getRuntime().availableProcessors();
// → 1 thread reserved for the reporter, rest are producers
```

On an 8-core machine: 7 producer threads + 1 reporter thread.

To cap CPU usage on a shared machine, hard-code the thread count:

```java
private static final int NUM_THREADS = 4;
```

## Dependencies

Managed via `build.gradle`:

| Library | Purpose |
|---|---|
| `org.apache.kafka:kafka-clients` | Kafka producer API |
| `com.fasterxml.jackson.core:jackson-databind` | JSON serialization |
| `org.projectlombok:lombok` | `@Data`, `@NoArgsConstructor`, `@AllArgsConstructor` on `Transaction` |
| `org.slf4j:slf4j-api` | Logging |

Lombok eliminates boilerplate getters, setters, and constructors from the `Transaction` DTO — the class stays clean and focused on the data model.
